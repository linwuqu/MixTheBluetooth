# 09 本地能力统一契约(键值 / 结构化 / 文件三件套)

> 状态:**已施工,归档可删**(其沉淀是代码:LocalPort / TinkKvStore / SqliteStore / OkioFileStore;下文代码块与真实代码逐字一致)
> 关联:[08-统一蓝牙管理器](./08-统一蓝牙管理器.md)(蓝牙同一套契约语言)、[03-端口挂载与业务适配器](./03-端口挂载与业务适配器.md)(能力挂载区现状)
> 本文件是**过程文档**:施工完成后价值转移给代码。

## 0. 一句话

本地三能力(键值 / 结构化 / 文件)收敛为**统一语境、按真实需求暴露**的契约族:
统一结果词汇(按返回域窄化:`KvReadResult` / `KvWriteResult` / `KvRemoveResult` / `FileDeleteResult`)、统一命名(`XxxStore`)、一个聚合口(`LocalPort`);
各自差异(加密 / SQL / 路径)收进实现内部;**不硬套统一骨架**——每类能力暴露什么,由真实需求决定
(文件分区按 app 完整形态规划,不是按当前实现裁剪)。

## 1. 现状与问题

### 1.1 现状代码面

```text
port/adapter/localport/
├─ LocalPort.kt                      # 文件名叫 LocalPort,里面却没有 LocalPort!
│    ├─ StringEntropy(接口)           # read/write/remove/contains
│    ├─ LocalFileClient(接口)         # source/sink/list/delete/prune
│    └─ 5 个散落 sealed:EntropyReadResult / EntropyWriteResult / EntropyRemoveResult /
│       FileDeleteResult / FilePruneResult + FileSpace/FileEntry/RetentionPolicy
├─ AndroidLocalPort.kt               # 聚合对象(entropy + sqlite + files)+ Tink 密钥管理
├─ entropy/TinkStringEntropy.kt      # 实现(接口名带技术词,读起来是"熵"不是"键值")
├─ database/LocalDatabaseFactory.kt  # SQLDelight 工厂:返回生成类 LocalDatabase(引擎裸奔)
└─ file/OkioLocalFileClient.kt       # 实现(Client 后缀,与契约/聚合不押韵)
```

上层消费(AppGraph):

```kotlin
private val kv: StringEntropy = androidLocal.entropy      // 键值存储(Tink 加密)
private val sqlite: LocalDatabase = androidLocal.sqlite   // 结构化存储(SQLDelight)
internal val files: LocalFileClient = androidLocal.files  // 文件(日志初始化使用)
```

### 1.2 问题一:没有统一语境,主看无处

- **契约文件货不对板**:`LocalPort.kt` 里没有 `LocalPort`;想"主看一处理解完整逻辑",打开文件看到三个互不押韵的接口 + 5 个结果类型堆在一起,没有主次。
- **结果词汇各自为政**:`EntropyReadResult.Found/Missing/Failed`、`EntropyWriteResult.Written/Failed`、`EntropyRemoveResult.Removed/Missing/Failed`、`FileDeleteResult.Deleted/Missing/Failed`、`FilePruneResult.Pruned/Failed`——5 套名字,形态全一样(成功 / 不存在 / 失败)。上层每接一个能力就要学一套新词汇。

### 1.3 问题二:命名无逻辑,复杂没留到实现内部

- `StringEntropy`——"字符串熵"?读代码才知道是加密键值存储;
- `LocalFileClient`——Client 后缀,与 `LocalDatabase`(引擎)、`TinkStringEntropy`(实现)不押韵;
- `AndroidLocalPort` 字段 `entropy / sqlite / files` 与类型名对不上(字段 `kv` 的类型却是 `StringEntropy`);
- `AndroidLocalPort` 工厂堆着 Tink 密钥管理(`AeadConfig.register` / `AndroidKeysetManager` / keystore URI),文件根目录映射也写在工厂里——拼装层不纯。

### 1.4 问题三:分区缺需求依据,策略混进契约

`FileSpace { LOGS, RECEIVED, OUTGOING, CACHE }` 四个分区,但从定义上看不出
"为什么是这四个、各自生命周期如何、由谁清理"——分区是功能名罗列,不是需求规划:

- **没有生命周期与存储属性定义**:四个分区全部塞在 `filesDir`(持久目录),
  连"临时产物放 cacheDir、由系统清理"这个 Android 官方分层的特性都没用上;
- **没有保留策略归属**:谁清理、何时清理、清理什么,散落在实现与使用方之间,
  读代码看不出意图;
- **`prune` + `RetentionPolicy` 是业务策略**(保留几个、删多旧),却长在契约里——
  日志轮转的需求混进了通用能力;
- **分区与完整需求没有对应关系**:app 的文件需求是日志系统 + 收发文件缓存 +
  HTTP(json)与算法(文件)互转的中转、以及未来统一 json 文件通信模型的存储基础——
  这些需要一个按生命周期规划的分区,而不是功能名罗列。

### 1.5 问题四:结构化没有契约(或过度契约)

- 现状:`ConnectionPortAdapter` 直接拿 SQLDelight 生成类(`sqlite.deviceBindingQueries.findByUserId(...)`),上层摸引擎;
- 过度契约也不行:每张表一个 Table 接口 + 行映射 + CRUD 收窄——全项目只有一张表,这个量级撑不起 repo/表接口设计,而且收窄接口反而**限制** SQL 能力(以后要 join / 自定义查询,接口挡路)。

### 1.6 根因小结

三个能力是三个独立引擎,引擎没错;错在契约层缺席或错位——没有统一语境与词汇、命名不押韵、分区缺需求依据、策略混入。修的就是契约层,而且**只按真实需求修,不硬套形状**。

## 2. 设计

### 2.1 统一落点(哪些统一,哪些不统一)

**统一(命名 / 词汇 / 聚合):**

1. **统一结果词汇**:按**返回域窄化**——读域 `KvReadResult`(Value/None/Failed)、写域 `KvWriteResult`(Done/Failed)、删域 `KvRemoveResult`(Done/None/Failed),文件删除同形 `FileDeleteResult`;方法签名只暴露本方法可能的结果,when 精确穷举、无不可达占位分支;
2. **统一命名**:契约接口 = 能力名 + `Store`;实现 = 技术前缀 + `Store`;聚合口 = `LocalPort`;
3. **一个聚合口**:AppGraph 只挂 `LocalPort`,`local.kv / local.sql / local.files` 三能力一步到位。

**不统一(每类能力按真实需求暴露,不硬套 CRUD 四向):**

| 能力 | 真实需求 | 暴露什么 |
|---|---|---|
| 键值 | Auth 增删改查 | read / write / remove / contains 四向 |
| 结构化 | Connection 查 / 写 / 删 | **浅壳**:SQLDelight 生成查询对象直接当契约,零收窄 |
| 文件 | 日志系统 + 收发文件缓存 + 互转中转 | read / write / list / delete 原子能力;**prune 等策略移出**,分区按完整需求规划(见 §2.3) |

**为什么不做 `execute(effect)` 单入口**:蓝牙的 execute 成立是因为单引擎单会话;本地三引擎无共享会话,文件是流式句柄(Source/Sink),SQL 是强类型查询——单入口只是转发壳,丢流式与类型。统一落在命名 / 词汇 / 聚合口上,主看契约文件即完整能力清单。

### 2.2 命名规则

| 位置 | 规则 | 例子 |
|---|---|---|
| 契约接口 | 能力名 + `Store` | `KvStore` / `SqlStore` / `FileStore` |
| 聚合口 | `LocalPort`(名实相符) | `LocalPort` |
| 实现 | 技术前缀 + `Store` | `TinkKvStore` / `SqliteStore` / `OkioFileStore` |
| kv 内部组件 | 职责名 | `KvStorage`(存储) / `KvCipher`(加密) |
| 实现子包 | 能力名 | `kv/` `sql/` `file/` |
| 统一结果 | 按返回域:`KvReadResult` / `KvWriteResult` / `KvRemoveResult` / `FileDeleteResult` | `Value / None / Done / Failed`(各域按需裁剪) |
| 测试替身 | `InMemory` + 契约名 | `InMemoryKvStore` / `FakeFileStore` |

### 2.3 契约 LocalPort.kt(全文)

```kotlin
package com.biosensor.migratedev.port.adapter.localport

import com.biosensor.migratedev.database.DeviceBindingQueries
import okio.Sink
import okio.Source

/** 键值读结果:读到值 / 不存在 / 失败。 */
sealed interface KvReadResult {
    data class Value(val value: String) : KvReadResult
    data object None : KvReadResult
    data class Failed(val message: String) : KvReadResult
}

/** 键值写结果:完成 / 失败。 */
sealed interface KvWriteResult {
    data object Done : KvWriteResult
    data class Failed(val message: String) : KvWriteResult
}

/** 键值删结果:删成功 / 本就不存在 / 失败。 */
sealed interface KvRemoveResult {
    data object Done : KvRemoveResult
    data object None : KvRemoveResult
    data class Failed(val message: String) : KvRemoveResult
}

/** 文件删结果:删成功 / 本就不存在 / 失败。 */
sealed interface FileDeleteResult {
    data object Done : FileDeleteResult
    data object None : FileDeleteResult
    data class Failed(val message: String) : FileDeleteResult
}

/** 键值存储:增删改查,加密在实现内部。 */
interface KvStore {
    suspend fun read(key: String): KvReadResult
    suspend fun write(key: String, value: String): KvWriteResult
    suspend fun remove(key: String): KvRemoveResult
    suspend fun contains(key: String): Boolean
}

/** 结构化存储浅壳:SQLDelight 生成查询对象直接当契约,不限制能力。 */
interface SqlStore {
    val deviceBinding: DeviceBindingQueries
}

/** 本地能力聚合口:键值 / 结构化 / 文件。 */
data class LocalPort(
    val kv: KvStore,
    val sql: SqlStore,
    val files: FileStore,
)

/** 文件分区:按生命周期与存储属性规划,依据是完整需求(日志 + 收发缓存 + 互转中转)。 */
enum class FileSpace {
    /** 诊断日志:持久,日志层按数量 + 时间轮转。 */
    LOGS,

    /** 接收缓存:算法数据落盘(如 CGM 缓存明文流),持久,业务层清理。 */
    RECEIVED,

    /** 发送缓存:待上传数据与转换产物,持久,发送确认后删。 */
    OUTGOING,

    /** 临时产物:可重建,系统可清理。 */
    CACHE,
}

/** 文件存储:原子能力,轮转 / 清理策略由使用方组合。 */
interface FileStore {
    fun read(space: FileSpace, relativePath: String): Source
    fun write(space: FileSpace, relativePath: String, append: Boolean = false): Sink
    fun list(space: FileSpace, relativePath: String = ""): List<FileEntry>
    fun delete(space: FileSpace, relativePath: String): FileDeleteResult
}

data class FileEntry(
    val relativePath: String, val size: Long?, val lastModifiedAtMillis: Long?
)
```

**返回域窄化的语义**(施工中按评审修订):同一份 `Value/None/Done/Failed` 形状按方法裁剪——
`read` 只可能 Value/None/Failed,`write` 只可能 Done/Failed,`remove`/文件 `delete` 只可能 Done/None/Failed;
消费方 when 只穷举本方法返回域,`error("不可达")` 占位分支与 `Value<*>` cast 一并消失。
`Value` 直接定 `String`(kv 全域只有字符串,泛型是伪通用)。

**与第一稿的差异(按评审意见):**

| 第一稿 | 第二稿 / 第三稿 | 理由 |
|---|---|---|
| 统一 CRUD 骨架(三域四向) | 能力按真实需求暴露 | 硬套在 sql 上限制能力、在文件上预置过剩 |
| `DeviceBindingTable` + `DeviceBindingRow` + 映射 | 删,浅壳直接持 `DeviceBindingQueries` | 表少量级不够,收窄反成限制;浅包装到此为止 |
| `FileSpace` 四分区(功能名罗列,全塞 filesDir) | 四分区保留,但按**生命周期与存储属性**规划:注释写明各分区需求与清理归属,CACHE 落 cacheDir | 分区是完整需求规划(日志 + 收发缓存 + 互转),不是当前实现的裁剪 |
| `prune` + `RetentionPolicy` + `FilePruneCount` 在契约 | 删,日志层自己组合 list+delete | 策略不进通用能力 |
| `TinkStringEntropy`(加密内嵌每方法) | `KvStorage` + `KvCipher` 两步组合(见 §2.4) | 主逻辑两步一眼看懂 |

### 2.4 实现 kv/TinkKvStore.kt(全文,两步组合)

```kotlin
package com.biosensor.migratedev.port.adapter.localport.kv

import android.content.Context
import androidx.datastore.core.DataStore
import androidx.datastore.preferences.core.PreferenceDataStoreFactory
import androidx.datastore.preferences.core.Preferences
import androidx.datastore.preferences.core.edit
import androidx.datastore.preferences.core.stringPreferencesKey
import androidx.datastore.preferences.preferencesDataStoreFile
import com.biosensor.migratedev.port.adapter.localport.KvReadResult
import com.biosensor.migratedev.port.adapter.localport.KvRemoveResult
import com.biosensor.migratedev.port.adapter.localport.KvStore
import com.biosensor.migratedev.port.adapter.localport.KvWriteResult
import com.google.crypto.tink.Aead
import com.google.crypto.tink.KeyTemplates
import com.google.crypto.tink.RegistryConfiguration
import com.google.crypto.tink.aead.AeadConfig
import com.google.crypto.tink.integration.android.AndroidKeysetManager
import kotlinx.coroutines.CoroutineScope
import kotlinx.coroutines.flow.first
import okio.ByteString.Companion.decodeBase64
import okio.ByteString.Companion.toByteString

/** 键值实现:两步组合——存储([KvStorage]) + 加密([KvCipher])。 */
internal class TinkKvStore(
    private val storage: KvStorage,
    private val cipher: KvCipher,
) : KvStore {

    companion object {
        fun create(context: Context, scope: CoroutineScope): KvStore {
            val application = context.applicationContext
            val dataStore = PreferenceDataStoreFactory.create(
                scope = scope,
                produceFile = { application.preferencesDataStoreFile(ENTROPY_DATASTORE_NAME) },
            )
            return TinkKvStore(
                storage = DataStoreKvStorage(dataStore),
                cipher = TinkAeadCipher(createAead(application)),
            )
        }

        private fun createAead(context: Context): Aead {
            AeadConfig.register()
            val keyset = AndroidKeysetManager.Builder()
                .withSharedPref(context, KEYSET_NAME, KEYSET_PREFERENCES_NAME)
                .withKeyTemplate(KeyTemplates.get("AES256_GCM"))
                .withMasterKeyUri(MASTER_KEY_URI)
                .build().keysetHandle
            return keyset.getPrimitive(RegistryConfiguration.get(), Aead::class.java)
        }

        private const val ENTROPY_DATASTORE_NAME = "string_entropy.preferences_pb"
        private const val KEYSET_NAME = "string_entropy_keyset"
        private const val KEYSET_PREFERENCES_NAME = "string_entropy_keyset_preferences"
        private const val MASTER_KEY_URI = "android-keystore://migratedev.string_entropy.master"
        private const val KEY_PREFIX = "entropy:"
    }

    override suspend fun read(key: String): KvReadResult = try {
        val stored = storage.read(preferenceKey(key)) ?: return KvReadResult.None
        KvReadResult.Value(cipher.decrypt(key, stored))
    } catch (failure: Exception) {
        KvReadResult.Failed(failure.message ?: "加密字符串读取失败")
    }

    override suspend fun write(key: String, value: String): KvWriteResult = try {
        storage.write(preferenceKey(key), cipher.encrypt(key, value))
        KvWriteResult.Done
    } catch (failure: Exception) {
        KvWriteResult.Failed(failure.message ?: "加密字符串写入失败")
    }

    override suspend fun remove(key: String): KvRemoveResult = try {
        if (storage.remove(preferenceKey(key))) KvRemoveResult.Done else KvRemoveResult.None
    } catch (failure: Exception) {
        KvRemoveResult.Failed(failure.message ?: "加密字符串删除失败")
    }

    override suspend fun contains(key: String): Boolean = try {
        storage.contains(preferenceKey(key))
    } catch (_: Exception) {
        false
    }

    private fun preferenceKey(key: String) = "$KEY_PREFIX$key"
}

/** 第一步:存储(DataStore 最小读写面)。 */
internal interface KvStorage {
    suspend fun read(key: String): String?

    suspend fun write(key: String, value: String)

    /** 返回 true 表示确实删掉了。 */
    suspend fun remove(key: String): Boolean

    suspend fun contains(key: String): Boolean
}

/** 第二步:加密(明文 ↔ 密文)。 */
internal interface KvCipher {
    fun encrypt(key: String, plaintext: String): String

    fun decrypt(key: String, ciphertext: String): String
}

private class DataStoreKvStorage(
    private val dataStore: DataStore<Preferences>,
) : KvStorage {
    override suspend fun read(key: String): String? =
        dataStore.data.first()[stringPreferencesKey(key)]

    override suspend fun write(key: String, value: String) {
        dataStore.edit { preferences ->
            preferences[stringPreferencesKey(key)] = value
        }
    }

    override suspend fun remove(key: String): Boolean {
        var existed = false
        dataStore.edit { preferences ->
            val preferenceKey = stringPreferencesKey(key)
            existed = preferences.contains(preferenceKey)
            preferences.remove(preferenceKey)
        }
        return existed
    }

    override suspend fun contains(key: String): Boolean =
        dataStore.data.first().contains(stringPreferencesKey(key))
}

internal class TinkAeadCipher(
    private val aead: Aead,
) : KvCipher {
    override fun encrypt(key: String, plaintext: String): String =
        aead.encrypt(plaintext.toByteArray(Charsets.UTF_8), associatedData(key))
            .toByteString().base64()

    override fun decrypt(key: String, ciphertext: String): String {
        val decoded = ciphertext.decodeBase64()?.toByteArray()
            ?: throw IllegalArgumentException("加密字符串格式无效")
        return aead.decrypt(decoded, associatedData(key)).toString(Charsets.UTF_8)
    }

    private fun associatedData(key: String): ByteArray =
        "$AAD_PREFIX$key".toByteArray(Charsets.UTF_8)

    private companion object {
        const val AAD_PREFIX = "migratedev/string-entropy/"
    }
}
```

**主逻辑形态**:`TinkKvStore` 本体只有四行组合(每个方法一行两段);加密细节全部在 `TinkAeadCipher`,存储细节全部在 `DataStoreKvStorage`。注意两点:存储 key 统一走 `entropy:` 前缀(`preferenceKey`),把 kv 域与其他 DataStore 数据隔离;AAD 用业务 key 绑定密文归属 key,密文挪到别的 key 解密必失败。测试也分两层:storage 假实现 + cipher 假实现,各自独立验证,再验证组合。

### 2.5 实现 sql/SqliteStore.kt(全文,浅壳)

package com.biosensor.migratedev.port.adapter.localport.sql

import android.content.Context

/** 结构化实现浅壳:查询对象直接暴露,不映射、不建表接口。 */

            val driver = AndroidSqliteDriver(
                schema = LocalDatabase.Schema,
                context = context.applicationContext,

            return SqliteStore(LocalDatabase(driver))
        }

        private const val DATABASE_NAME = "migratedev.db"
    }
}

### 2.6 实现 file/OkioFileStore.kt(全文,原子能力)

```kotlin
package com.biosensor.migratedev.port.adapter.localport.file

import android.content.Context
import com.biosensor.migratedev.port.adapter.localport.FileDeleteResult
import com.biosensor.migratedev.port.adapter.localport.FileEntry
import com.biosensor.migratedev.port.adapter.localport.FileSpace
import com.biosensor.migratedev.port.adapter.localport.FileStore
import okio.FileSystem
import okio.Path
import okio.Path.Companion.toPath
import okio.Sink
import okio.Source

class OkioFileStore internal constructor(
    private val fileSystem: FileSystem,
    roots: Map<FileSpace, Path>,
) : FileStore {

    private val roots = roots.mapValues { (_, path) ->
        path.toString().toPath(normalize = true)
    }

    init {
        require(FileSpace.entries.all(roots::containsKey)) {
            "每个文件分区都需要根目录"
        }
    }

    companion object {
        /** 分区根目录:业务数据放 filesDir(持久),临时产物放 cacheDir(系统可清)。 */
        fun create(context: Context): FileStore {
            val application = context.applicationContext
            return OkioFileStore(
                fileSystem = FileSystem.SYSTEM,
                roots = mapOf(
                    FileSpace.LOGS to application.filesDir.resolve("logs").absolutePath.toPath(),
                    FileSpace.RECEIVED to application.filesDir.resolve("received").absolutePath.toPath(),
                    FileSpace.OUTGOING to application.filesDir.resolve("outgoing").absolutePath.toPath(),
                    FileSpace.CACHE to application.cacheDir.resolve("cache").absolutePath.toPath(),
                ),
            )
        }
    }

    override fun read(space: FileSpace, relativePath: String): Source =
        fileSystem.source(resolve(space, relativePath))

    override fun write(space: FileSpace, relativePath: String, append: Boolean): Sink {
        val path = resolve(space, relativePath)
        path.parent?.let(fileSystem::createDirectories)
        return if (append) {
            fileSystem.appendingSink(path)
        } else {
            fileSystem.sink(path)
        }
    }

    override fun list(space: FileSpace, relativePath: String): List<FileEntry> {
        val root = roots.getValue(space)
        val directory = resolve(space, relativePath)
        return collectFiles(directory).mapNotNull { path ->
            val metadata = fileSystem.metadataOrNull(path) ?: return@mapNotNull null
            if (metadata.isDirectory) {
                null
            } else {
                FileEntry(
                    relativePath = path.relativeTo(root).toString(),
                    size = metadata.size,
                    lastModifiedAtMillis = metadata.lastModifiedAtMillis,
                )
            }
        }.sortedBy(FileEntry::relativePath)
    }

    override fun delete(space: FileSpace, relativePath: String): FileDeleteResult {
        val path = resolve(space, relativePath)
        if (!fileSystem.exists(path)) {
            return FileDeleteResult.None
        }
        return try {
            fileSystem.delete(path)
            FileDeleteResult.Done
        } catch (failure: Exception) {
            FileDeleteResult.Failed(failure.message ?: "文件删除失败")
        }
    }

    private fun resolve(space: FileSpace, relativePath: String): Path {
        val root = roots.getValue(space)
        val candidate = root.resolve(
            relativePath.toPath(), normalize = true
        )
        require(
            candidate.segments.size >= root.segments.size
                && candidate.segments.take(root.segments.size) == root.segments
        ) {
            "路径逃逸出 ${space.name} 根目录"
        }
        return candidate
    }

    private fun collectFiles(directory: Path): List<Path> {
        val children = fileSystem.listOrNull(directory).orEmpty()
        return children.flatMap { child ->
            if (fileSystem.metadata(child).isDirectory) {
                collectFiles(child)
            } else {
                listOf(child)
            }
        }
    }
}
```

internal class InMemoryKvStore : KvStore {
    val values = mutableMapOf<String, String>()

    override suspend fun read(key: String): KvReadResult =
        values[key]?.let { KvReadResult.Value(it) } ?: KvReadResult.None

    override suspend fun write(key: String, value: String): KvWriteResult {
        values[key] = value
        return KvWriteResult.Done

    override suspend fun remove(key: String): KvRemoveResult =

    override suspend fun contains(key: String): Boolean = values.containsKey(key)

## 3. 诚实评估

### 3.1 SQL 浅壳的取舍

浅壳引用 SQLDelight 生成类型(`DeviceBindingQueries`),契约与引擎类型耦合——换来 SQL 能力零限制、零映射成本。权衡:全项目一张表,表接口 + 行映射是过度设计;未来表多了(3 张以上)再考虑每表收窄,届时 SqlStore 加属性即可,不推倒重来。

### 3.2 FileSpace 分区依据(按完整需求,不按当前实现)

分区不是"当前谁在用"的裁剪,而是 **app 完整文件需求的规划**——日志系统 +
收发文件缓存 + 互转中转。依据 Android 官方存储分层(filesDir 持久 /
cacheDir 系统可清)与需求,四个分区各有生命周期与清理归属:

| 分区 | 需求 | 存储属性 | 清理策略归属 |
|---|---|---|---|
| LOGS | 诊断日志(ReleaseTree 写) | filesDir/logs 持久 | 日志层轮转(数量 + 时间) |
| RECEIVED | 接收缓存:算法数据落盘(CGM 缓存明文流) | filesDir/received 持久 | 业务层(时间 / 容量) |
| OUTGOING | 发送缓存:待上传数据与转换产物 | filesDir/outgoing 持久 | 业务层(发送确认后删) |
| CACHE | 临时中间产物,可重建 | cacheDir 系统可清 | 系统配额 + 可选容量清理 |

互转流向(HTTP 用 json、算法用文件,文件系统是中转载体):

```text
算法(文件流) --写--> RECEIVED --读--> 转换(json) --写--> OUTGOING --读--> HTTP 上传
```

**演进**:未来统一为 json 文件通信模型时,所有交换数据以文件落盘——FileStore
只管字节流,不感知格式(json / 二进制),天然兼容;分区规划为此预留存储基础,
这也是"不可能全放内存"的落点。

**现状 OUTGOING / CACHE 暂无调用方**:这是"需求已规划、实现未落地",不是
"没有需求"——收发文件缓存的发送端与互转中转是 app 形态的一部分,契约先行;
根目录惰性创建(写入时才 mkdir),不产生成本。

**prune 移出契约的依据**:轮转(保留几个、删多旧)是日志业务的策略,不是文件系统的
通用能力;通用能力只留 read / write / list / delete 四个原子操作,策略由使用方
(日志层)用原子能力自己组合——契约更薄,策略更贴近业务。

### 3.3 窄域结果的取舍(施工中修订)

第一版用统一 `LocalResult` 四分支,消费方 when 被迫穷举本方法不可能的形态——`Value<*>` 要 `as String`,`Done`/`Value` 在 read/remove 域各占一个 `error("不可达")` 分支。施工中按评审改为**按返回域窄化**:同一批形态按方法裁剪成 `KvReadResult`(Value/None/Failed)、`KvWriteResult`(Done/Failed)、`KvRemoveResult`(Done/None/Failed)、`FileDeleteResult`(与删域同形)。

- **代价**:词汇从 1 套变 4 个类型(形状统一,按方法记返回域);
- **收益**:when 精确穷举——read/remove 三分支、write 两分支,占位分支与 cast 全消失;`Value` 定死 `String`(kv 全域只有字符串,泛型是伪通用);
- **边界**:sql 域不使用结果词汇(浅壳直接返回生成行类型);`None` 在 read(没存过)与 remove(本就不存在)语义不同,但消费方按"该状态已达成"合并处理,如 auth 的 `Done, None -> SessionCleared`。

### 3.4 影响面

- 主代码 10 个文件:契约 1 重写、实现 3 落地(1 新结构 2 改名)、拼装 1 薄化、上层 5 处换接口(ReleaseTree 多一处轮转策略回本地);
- 测试 9 个文件:全在同模块,改名 + 断言换词汇;
- **行为零变化**:引擎(Tink / SQLDelight / okio)、存储键名、数据库名、keyset 名、全部四个分区根路径都不动——存量数据不受影响。CACHE 根目录维持现状(cacheDir/cache,施工前即如此),本次只是把"临时产物归系统可清目录"的分区语义写进契约与实现注释,无路径变化、无存量迁移成本。

### 3.5 不改什么

- 不换引擎(Tink / SQLDelight / okio 继续用);
- 不做统一事务 / 统一队列(当前无跨域事务需求);
- 不动 `database/` 包与 `DeviceBinding.sq`(引擎与 schema 是生成物,保持原样);
- 不做 repo / DAO 设计(表量级不够)。
