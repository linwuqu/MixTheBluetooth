## 2. 设计（After）

### 2.1 角色与职责

先把参与这件事的角色逐个列清楚，每个一句话，括号里是实现：

|---|---|
| 上传决策核 | 只记"文件推出去了没、任务号多少、查了几次、结果拉到了没"，拍板下一步是继续查还是收工；纯函数，不做 IO（`decisioncore/upload/UploadDecision.kt`） |

### 2.2 合作过程

逐个场景写"谁做了什么，怎么配合"。

**正常一次（读完之后上传）**

1. 读到缓存文件后，用户切到"分析结果"页签，点"上传分析"（用 `CgmIntent.UploadDataset` 实现）。
2. 翻译层先查冲突：读或短命令在跑就拒绝并提示等待（用现有的 `blocked()` 实现）；否则算出本机文件路径 `cgm/{设备号}.txt`（用 `cgmCachePath(deviceId)` 实现），发给上传编排器（用 `UploadEvent.UploadRequested(path)` 实现）。
3. 决策核从 `Idle` 走到 `Uploading`，排出推文件（用 `UploadEffect.UploadDataset(path)` 实现）。
4. 端口从 `FileStore` 读出文件文本，转成 UTF-8 字节；`identify = 文件名_字节数_时间戳` 里的字节数就用这份字节的长度（与请求体逐字节一致，不另算）。然后组 multipart，带 `token` 头推到 `POST /api/cgm/v1/dataset/upload`（用 `http.invoke { api.upload(...) }` 实现）。
5. 端口按旧 app 的判据放行：HTTP 成功 且 业务码 ok 且 data 非空 且 `datasetStatus == "VALID"` 且 `jobId` 非空。全过 → 报 `DatasetAccepted(jobId, datasetId)`；任一项不过 → 报 `DatasetRejected(原因)`。
6. 决策核进 `Polling`，排出查任务（用 `UploadEffect.PollJob(jobId)` 实现）；端口在调用前先等 1500ms。
7. 任务没完 → 端口报 `JobPending(status)`，决策核计数加一；不到 3 次就再排一次 `PollJob`，到 3 次报 `PollExhausted` 进 `Failed`。
8. 任务成功 → 端口报 `JobSucceeded(resultId)`，决策核进 `Fetching`，排出拉结果（用 `UploadEffect.FetchResult(jobId, datasetId, resultId)` 实现）。
9. 端口并发拉 `info` 与 `curve`，合并成一份结果（用 `UploadPortAdapter.fetchResult()` 实现），报 `ResultFetched(result)`。两条都失败才算失败，只成一条也返回。
10. 决策核进 `Done`。翻译层把结果放进 `CgmUiState.result`，界面显示面板：主数值、单位页签、曲线、统计、点列表。

**异常场：网络不通**

端口报 `TransferFailed(原因)`，决策核进 `Failed`。本地文件不动，按钮可以再点一次，从头传。

**边界场一：本地还没有文件**

端口一个请求都不发，直接报 `FileMissing`，决策核进 `Failed("尚未生成缓存文件，请先读缓存")`。

**边界场二：上传中设备掉线**

上传只走 HTTP，与蓝牙无关：连接域照常重连，上传照常继续；反过来也一样。

### 2.3 配合规则

**用四句话概括合作规矩：**

1. 上传不碰蓝牙，读流程不碰网络；两边互不阻塞，只在翻译层互斥（读/短命令在跑时拒绝上传）。
2. 决策核只数次数、判状态，不 sleep、不发请求；等待和 HTTP 都在端口。
3. 端口一次 effect 只发一组请求，不自己重试、不自己发散——重试与否是决策核的事。
4. 结果只在内存里放着，不落库、不跨会话保留（与旧 app 一致）。

### 2.6 数据流

```
点"上传分析"
   → CgmIntent.UploadDataset
   → 查冲突（读/短命令在跑就拒绝）
   → 算路径 cgmCachePath(deviceId)
   → UploadEvent.UploadRequested
   → UploadState.Uploading
   → UploadEffect.UploadDataset
      → 端口：取文件大小 → 组 identify → 组 multipart → POST /dataset/upload
      → DatasetAccepted(jobId, datasetId)      ├ 判据全过
      → DatasetRejected(原因) / TransferFailed / FileMissing
   → UploadState.Polling(attempt = 1)
   → UploadEffect.PollJob  →（端口先等 1500ms）→ GET /jobs/{jobId}
      → JobPending(status)   → attempt + 1，不足 3 次再排一次
      → JobSucceeded(resultId) → UploadState.Fetching
      → JobFailed(原因) / TransferFailed → Failed
      → 三次都没完 → PollExhausted → Failed
   → UploadEffect.FetchResult
      → 端口并发拉 GET /predictions/{id}/info + /curve → 合并
      → ResultFetched(CgmResult)
   → UploadState.Done
   → CgmUiState.result → CgmResultPanel 渲染
```

## 3. 诚实评估

| 维度 | 说明 |
|---|---|
| 改善了什么 | 上传与读缓存彻底分开：网络慢、后端挂掉、重试，都不会拖住蓝牙读流程；反过来设备掉线也不影响上传。上传的节奏全在纯函数状态机里，可单测，不靠真机复现。 |
| 代价与边界 | ① 多了一层 port + decisioncore + orchestrator（约 4 个新文件），比"在 CgmPortAdapter 里直接发 HTTP"要多写代码——换来的是可测和可换。② 轮询上限沿用旧 app 的 3 次 × 1500ms，最长等 4.5 秒；后端任务若普遍更慢，这里会误判失败（常量留成可调）。③ 上传没有队列、没有断点续传、没有持久化重试，失败要靠用户再点一次——旧 app 也是这样。④ 结果不落库，退出页面就没了。 |
| 不做什么 | 不做上传队列与后台续传；不做历史结果列表；不做 `POST /api/file/v1/upload`（那是通用文件接口，本期用不上）；不动 `RootDecision` 的 `CgmCompletedEvent`（仍保持"只记录不切页"——上传改由按钮触发，不经 Root）；不引图表库。 |

**待确认（写代码前要定）**

| # | 问题 | 我方建议 |
|---|---|---|
| 1 | `identify` 与文件名的形态。旧 app 是 `{yyyy-MM-dd}CGM_Cache_data.txt`；我们现在是 `{设备号}.txt`。后端若按文件名解析或去重，改名会出问题。 | 保持设备维度命名（01-数据上云 要建设备表，文件名带设备号正好对应），`identify` 格式仍是 `名字_字节数_时间戳`。**需向后端确认**。 |
| 2 | 上传是自动还是手动。旧 app 是读校验通过后自动上传。 | 手动按钮。理由：网络是外部资源，失败要等重试，不该在读流程里隐式发生；且允许用户重复上传同一文件（旧 app 也是保留文件手动重传）。 |
| 3 | 图表怎么做。旧 app 有 MPAndroidChart，CGM 那张图是自绘的 694 行自定义 View。migratedev 没有图表库。 | 用 Compose `Canvas` 自绘，不加依赖——要画的东西（折线 + 阈值带 + 点击取值）用 Canvas 完全够。 |
