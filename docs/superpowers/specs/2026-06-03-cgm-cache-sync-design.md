# CGM Cache Sync Design

Date: 2026-06-03

## Purpose

The current CGM flow treats each decoded Bluetooth callback as if it were a complete replay line. That makes the workflow hard to debug and unsafe around incomplete cache reads. The next design should model the operation as syncing one EEPROM cache replay from the device to the app:

1. Send the existing `ALL` command to read the device cache.
2. Receive decoded text chunks and assemble a replay document.
3. Validate the replay document locally.
4. Retry by sending `ALL` again when the replay is incomplete or invalid.
5. Upload only a validated local txt file.
6. Send the existing `DELETE` command only after upload succeeds.
7. Treat device text `Log Cleared` as the hardware acknowledgement that EEPROM cache deletion succeeded.

This design intentionally avoids a new packet protocol, ACK/NACK, sequence numbers, CRC, or Merkle tree in this phase.

## Current Evidence

The existing command strings are:

- `CgmCommands.LegacyCgm.readCache()` -> `ALL\n\r`
- `CgmCommands.LegacyCgm.deleteCache()` -> `DELETE\n\r`

The delete button only sends `DELETE`; it does not currently track a confirmation.

`Log Cleared` is not generated by app code and is not present as a source constant. It should be treated as hardware text observed over Bluetooth, and in this phase it is the delete acknowledgement.

`Analysis.java` is a codec/helper area. Its `detection()` method checks whether text contains non-hex characters for hex input filtering. It is not a CGM replay line-boundary or file-integrity validator.

## Non-Goals

- Do not introduce a new hardware protocol in this phase.
- Do not require firmware changes.
- Do not implement ACK/NACK, sequence numbers, per-chunk CRC, or Merkle verification.
- Do not move CGM business rules into `Analysis.java`.
- Do not delete device cache before local validation and server upload success.

## Architecture

Keep the layers separated:

```text
Bluetooth callback byte[]
  -> codec decode
  -> CGM cache sync session
  -> replay document validation
  -> local txt write
  -> upload/poll
  -> delete command
  -> delete confirmation
```

### Codec Layer

Existing responsibility:

- Convert `byte[]` to `String` using the configured encoding.
- Convert command `String` to `byte[]`.

This layer should not know about:

- `Start Playback`
- `Playback all done`
- `Log Cleared`
- replay retry
- upload
- delete confirmation

### CGM Cache Sync Buffer

Add one application-layer buffer/session object that owns one cache-read attempt and the retry loop. Keep this intentionally compact. The current phase does not need several small classes for document, validator, writer, and delete tracking.

Suggested class:

```text
app/src/main/java/com/hc/mixthebluetooth/application/cgm/CgmCacheSyncBuffer.java
```

Responsibilities:

- Accept decoded text chunks from Bluetooth.
- Preserve chunk boundaries enough to assemble replay lines.
- Track whether replay has started and completed.
- Keep the replay document in memory.
- Validate completeness and basic schema.
- Decide whether to retry by sending `ALL` again.
- Write the validated replay once to txt.
- Confirm cache deletion when `Log Cleared` is received.
- Surface state changes to the workflow.

The session should not send Bluetooth bytes directly. It should return commands/actions to the caller so UI/application boundaries stay clear.

Core methods:

```text
acceptChunk(String chunk)
  Synchronizes newly decoded data into the buffer and emits any complete replay lines.

validate()
  Checks Start Playback, Playback all done, data-line presence, marker order, and simple schema diagnostics.

shouldRetry()
  Returns true when the current attempt is incomplete/invalid and the retry budget is not exhausted.

writeTo(File dir/dateProvider)
  Writes the validated replay txt once.

acceptDeviceLine(String line)
  Confirms delete when line contains Log Cleared.
```

Validation should return structured diagnostics, not just `true`/`false`.

Important rule:

`Log Cleared` is treated as the hardware acknowledgement for successful cache deletion. No additional app-specific ACK protocol is introduced in this phase.

### Delete Button Confirmation

Manual delete remains dangerous because EEPROM data is valuable. The `删除缓存` button should require a second confirmation before sending `DELETE`.

UI behavior:

- User taps `删除缓存`.
- Show a confirmation dialog explaining that device cache will be erased.
- Only after confirmation does the app send `DELETE\n\r`.
- The app waits for `Log Cleared` as the hardware acknowledgement.

This protects against accidental deletion. Automatic deletion after successful upload still waits for `Log Cleared`, but it does not need the manual dialog because it is initiated by workflow success rather than a casual tap.

## State Model

There are two related but different concepts:

1. **Session state**: long-lived state held by `CgmCacheSyncBuffer` / workflow. It answers "where is this cache sync process now?"
2. **Step result**: short-lived result returned after one input/action. It answers "what just happened because of this chunk, validation, upload callback, or delete confirmation?"

Do not merge these two concepts in implementation. A session state persists across many Bluetooth chunks and network callbacks. A step result is consumed immediately by the caller to update UI, send a command, or start upload.

### Session State

Session state should be stored by the cache sync workflow/buffer and should be the source of truth for the current replay process.

```text
IDLE
READING_CACHE
VALIDATING
RETRYING
READY_TO_UPLOAD
UPLOADING
WAITING_DELETE_CONFIRM
DONE
ERROR
```

State responsibilities:

```text
IDLE
No cache sync is active. The buffer is empty or reset. A user action can start a cache read by sending ALL.

READING_CACHE
The app has sent ALL and is accepting device text chunks. The buffer may have partial text, complete lines, or a partially received replay. This is the only state where normal replay data should be appended.

VALIDATING
The replay end marker has been observed, or a timeout/retry condition requires checking the current buffer. The app is checking completeness and schema. This state should be brief and synchronous in the first implementation.

RETRYING
The current attempt is incomplete or invalid, and retry budget remains. The workflow should request another ALL, reset only the current attempt data, and then return to READING_CACHE.

READY_TO_UPLOAD
The replay document is valid and has been written to local txt. The file is ready to be uploaded. No more replay lines should be appended to this document.

UPLOADING
The app has started upload/poll. The device cache must not be deleted yet. Failure here should leave EEPROM untouched and surface an error or allow retry.

WAITING_DELETE_CONFIRM
Upload/poll has succeeded and the app has sent DELETE. The app is waiting for the device text Log Cleared, which is treated as the hardware acknowledgement that cache deletion succeeded.

DONE
The app has uploaded the replay and confirmed device cache deletion, or has otherwise reached a terminal success state documented by the workflow.

ERROR
The sync failed and cannot continue automatically. The buffer should keep diagnostics so UI/logcat can explain the reason.
```

Initial read:

```text
User presses read cache
  -> App sends ALL
  -> state = READING_CACHE
```

Receiving replay:

```text
Bluetooth text arrives
  -> session accepts chunk
  -> session assembles lines
  -> session updates replay document
```

Completion:

```text
Playback all done observed
  -> validate document
  -> if valid: write txt once, upload
  -> if invalid: retry ALL if retry budget remains
```

Retry:

```text
invalid or timeout
  -> if retryCount < maxRetries: send ALL again, reset current attempt
  -> else: report diagnostic error
```

Delete:

```text
upload/poll succeeds
  -> App sends DELETE
  -> delete tracker enters pending state
  -> if Log Cleared arrives: DONE
  -> else: upload remains successful, but deletion is unconfirmed
```

### Step Result

Avoid callback spam for every line. Instead, the session/workflow should return step results from individual operations.

```text
IGNORED
READ_STARTED
LINE_APPENDED
REPLAY_VALID
RETRY_REQUESTED
UPLOAD_STARTED
UPLOAD_SUCCEEDED
DELETE_SENT
DELETE_CONFIRMED
ERROR
```

Step result responsibilities:

```text
IGNORED
The input did not affect the CGM cache sync. Example: unrelated device text while IDLE, or Log Cleared when no DELETE is pending.

READ_STARTED
The workflow accepted a read-cache request and should send ALL, or has just entered READING_CACHE after ALL.

LINE_APPENDED
A complete replay line was accepted into the current buffer. This is useful for diagnostics/counters, but should not normally trigger UI work for every line.

REPLAY_VALID
The current buffer passed validation and is ready to be written/uploaded. The session state should move toward READY_TO_UPLOAD.

RETRY_REQUESTED
The current attempt failed validation or timed out, but retry budget remains. The caller should send ALL again. This result must include a diagnostic reason.

UPLOAD_STARTED
A valid txt file has been produced and upload/poll has started. Session state becomes UPLOADING.

UPLOAD_SUCCEEDED
Server-side upload/poll reached the accepted/generated success condition. The caller may now send DELETE. Session state should move toward WAITING_DELETE_CONFIRM after DELETE is sent.

DELETE_SENT
The app sent DELETE and is now waiting for device confirmation. This should only happen after upload success for automatic delete, or after manual user confirmation for manual delete.

DELETE_CONFIRMED
The app received Log Cleared. Session state can become DONE.

ERROR
The operation failed. The result must include diagnostics: missing start, missing end, invalid schema, retry limit exceeded, upload failed, or delete confirmation timed out.
```

Mapping rule:

- Session state is owned by the workflow/buffer.
- Step result is returned to the caller.
- UI should react to `READ_STARTED`, `RETRY_REQUESTED`, `UPLOAD_STARTED`, `UPLOAD_SUCCEEDED`, `DELETE_SENT`, `DELETE_CONFIRMED`, and `ERROR`.
- UI should usually ignore or aggregate `LINE_APPENDED`.
- `IGNORED` should not change UI unless debug logging is enabled.

## File/Package Boundary

Expected new or changed files:

- `application/cgm/CgmCacheSyncBuffer.java`
- `application/cgm/DefaultCgmWorkflow.java`
- `ui/cgm/CgmProfile.java`
- `ui/cgm/CgmController.java` only if the raw text path must preserve newlines before session processing
- `ui/cgm/CgmFragment.java` or action handling path for the manual delete confirmation dialog
- Unit tests under `app/src/test/java/com/hc/mixthebluetooth/application/cgm/`

Files that should not take CGM replay responsibility:

- `driver/implementation/codec/Analysis.java`
- `driver/implementation/codec/AnalysisTextCodec.java`
- Bluetooth transport/controller classes, except for logging or raw byte delivery

## Testing Plan

Unit tests should cover:

- Chunk split across line boundary:
  - `"Start Play"` + `"back\n"`
- Multiple lines in one chunk:
  - `"Start Playback\nEIS:...\nPlayback all done\n"`
- End marker without trailing newline:
  - `"Playback all done"`
- Missing start marker.
- Missing end marker.
- End before start.
- Empty replay.
- Retry sends `ALL` again after invalid attempt.
- Retry limit produces clear error.
- Valid replay writes one complete txt file.
- Upload success sends `DELETE`.
- `Log Cleared` confirms cache deletion.
- Manual delete button does not send `DELETE` until the user confirms.
- Manual delete button does not send `DELETE` until the user confirms.

Integration/manual checks:

- Log `BT_RECV bytes=... text=...` during real device cache read.
- Log session state transitions.
- Verify generated txt contains both `Start Playback` and `Playback all done`.
- Verify Python/static backend receives complete txt.
- Verify `DELETE` is not sent when upload fails.

## Open Decisions

1. Retry limit: recommended initial value is 2 or 3 cache-read attempts.
2. Timeout: choose a practical timeout after `Start Playback` if `Playback all done` never arrives.
3. Unknown lines: decide whether they are warnings or fatal schema errors in the first implementation.
4. Delete confirmation timeout: choose a short pending window, for example 5 seconds.
5. Whether upload success means `upload` accepted or `poll` reached `GENERATED`; recommended: delete only after generated/accepted final success, not after upload alone.

## Recommended First Implementation Scope

Implement app-only cache sync with:

- one compact in-memory cache-sync buffer,
- local schema validation,
- retry by re-sending `ALL`,
- one-shot txt write after validation,
- upload after txt write,
- send `DELETE` after upload/poll success,
- confirm delete on contextual `Log Cleared`.
- manual delete confirmation before user-initiated delete.

Defer:

- ACK/NACK,
- chunk CRC,
- Merkle tree,
- firmware changes.
