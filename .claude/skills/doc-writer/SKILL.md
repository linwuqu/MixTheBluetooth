# doc-writer:文档工作流

## 0. 核心概念(必须理解)

```text
需求(源头,保留)
  → 对话(与用户讨论对齐,不写文档)
  → 架构(过程文档:详细阐述与迭代,施工后退役,不是沉淀)
  → 施工(代码,最终沉淀)
  → 业务说明书(Workflow/,沉淀,了解项目的最小切面)
```

- **架构是过程**:它的价值在施工完成后转移给代码。施工完成 → 标记"已施工,归档可删"。不要求永远维护架构文档。
- **Workflow 是沉淀**:业务说明书(状态机/词汇/数据流/UI 对应),了解一个业务时**从 Workflow 看起**。
- **需求是源头**:用户提出的诉求,长期保留。
- **说明/ 四件套**(项目树/拓扑/词汇表/演进史)是静态快照,结构性变更时更新。

## 1. 文档四类与位置

| 类型 | 位置 | 生命周期 | 模板 |
|---|---|---|---|
| 需求 | `docs/SOP/需求/` | 源头,保留 | [templates/需求.md](./templates/需求.md) |
| 架构 | `docs/SOP/架构/` | 过程,施工后退役 | [templates/架构.md](./templates/架构.md) |
| 业务说明书 | `docs/SOP/Workflow/` | 沉淀,长期维护 | [templates/工作流.md](./templates/工作流.md) |
| 简报 | `docs/SOP/简报/` | 按需生成 | [templates/简报.md](./templates/简报.md) |

## 2. 流程(严格按阶段执行)

### 阶段 1:需求与对话对齐
1. 用户在需求提出(或对话中提到新诉求)→ 在 `需求/` 记录(一句话 + 原始诉求 + 状态)。
2. **禁止直接写设计文档**。先与用户对话:讨论"要什么 / 边界 / 怎么做 / 拆几步",用提问引导,不写方案。
3. 达成大致一致 → 阶段 2。

### 阶段 2:架构阐述与迭代
1. 在 `架构/` 写详细设计(模板:现状 → 设计 → 诚实评估 → 落地顺序)。
2. 与用户逐段对话迭代(一次只改一段,讨论完再继续)。
3. 用户认可 → 阶段 3。

### 阶段 3:施工与沉淀
1. 实现代码(每步可编译,测试回归)。
2. 施工完成后:**把最终形态沉淀为业务说明书**写入 `Workflow/`(状态机/词汇/数据流/UI 对应/变更记录)——架构文档里的细节不需要搬入,业务说明书只留业务视角。
3. 架构文档标题或开头加"已施工,归档可删"(不删除文件,除非用户要求)。
4. 更新 `说明/` 四件套(项目树/拓扑/词汇表/演进史)+ 索引(CONTENT.md、需求清单)。

### 阶段 4:简报(按需)
用户要汇报时:从 git log + `说明/演进史.md` 整理,**由大到小**:本周大主题 → 每个主题的支撑细节 → 遇到的问题与结论 → 下一步。写入 `简报/YYYY-MM-DD-主题.md`。

## 3. 编号规则(三个空间独立)

| 空间 | 规则 | 示例 |
|---|---|---|
| Workflow | `NN-中文名.md`,主序列从 01 起,沉淀 | `02-设备连接.md` |
| 架构 | `NN-中文名.md`,独立序列从 01 起,过程 | `04-词汇统一与契约收尾.md` |
| 需求 | `NN-需求名.md`,独立序列从 01 起 | `01-数据上云.md` |
| 简报 | `YYYY-MM-DD-主题.md` | `2026-07-24-第二次汇报.md` |
| 说明 | 固定名 | `项目树.md` 等 |

编号是引用锚点:重命名必须同步所有引用(见 rules.md 联动清单)。

## 4. 统一骨架与口吻

- 设计类文档五段:`0 一句话 / 1 现状 / 2 设计 / 3 诚实评估 / 4 落地与演进`。
- 全中文;短句;表格对比;**诚实评估是硬要求**(代价/边界/不做的事)。
- 词汇必须与 `说明/词汇表.md` 一致(Effect/Event,禁止 Command/Result)。
- 文档中的代码块必须与真实代码一致,写完后 Grep 核对。

## 5. 完成后检查清单

- [ ] 流程阶段正确(没跳过对话直接写架构)
- [ ] 位置正确(四类不混淆)
- [ ] 词汇与词汇表一致
- [ ] 代码引用与真实代码一致
- [ ] 索引(CONTENT/清单)已更新
- [ ] 变更记录已追加
- [ ] 架构文档:已施工的标记了"归档可删";Workflow:沉淀完整
