# doc-writer:文档写作与维护规范

## 0. 目的

保证 `docs/SOP/` 是一套**结构稳定、口吻统一、随开发滚动更新**的文档体系:
- 讲清楚我们怎么做的(架构)、做了什么(演进)、长什么样(项目树/拓扑/词汇)。
- 分类清晰:需求 / 设计(业务+架构)/ 简报 / 说明,互不混淆。
- 任何文档都能被"写第 0 次的人"读懂,也能被"三个月后的我们"续写。

## 1. 文档四分类

| 类型 | 位置 | 内容 | 触发 |
|---|---|---|---|
| 需求 | `docs/SOP/需求/` | 原始需求(用户提出的业务诉求),清单在 00-需求清单.md,单条推进时拆独立文件 | 新需求出现 |
| 设计-业务 | `docs/SOP/Workflow/` | 业务工作流(注册登录、设备连接、缓存输入输出流等):状态机、词汇、数据流 | 业务实现前写初稿,实现后回填 |
| 设计-架构 | `docs/SOP/架构/` | 跨业务的结构性设计(编排器、端口挂载、词汇统一、UI 分层、流建模) | 架构决策时 |
| 简报 | `docs/SOP/简报/` | 周期性汇报(做了什么、下一步),文件名带日期 | 汇报前 |
| 说明 | `docs/SOP/说明/` | 沉淀:项目树(覆盖面)、拓扑(结构)、词汇表(统一词汇)、演进史(阶段故事线) | 结构性变更后更新 |

> 判断归属的一句话:**"这是一个具体业务的流程"→ Workflow;** "它是跨业务的结构决策" → 架构; "是用户要什么" → 需求; "是阶段性汇报" → 简报; "是静态事实快照" → 说明。

## 2. 统一骨架(所有设计类文档)

```
# 标题(一句话:这是什么)

## 0. 一句话说明       ← 3 行内:本文件讲什么、为什么存在、服务谁
## 1. 现状(Before)     ← 动机:痛点、当前实现、要回答的问题
## 2. 设计(After)      ← 怎么做:拓扑/数据流/契约,代码块 + mermaid + 表格
## 3. 诚实评估          ← 代价、边界、取舍;明确"不做什么/不覆盖什么"
## 4. 落地与演进        ← 状态标记(初稿/梳理稿/修订稿/已落地)+ 变更记录表
```

简报用 `## 本周主要做的事情 / 下一步` 结构;说明类用各自固定小节 + `## 变更记录` 结尾。

## 3. 写作流程

1. **识别类型** → 见第 1 节;拿不准先问用户或对照 CONTENT。
2. **加载模板** → 从 `templates/` 复制对应模板(设计/需求/简报/说明)。
3. **按骨架写** → 先写 0/1/2 节(设计前),实现后回填代码与修正。
4. **统一口吻** → 中文;短句;用表格对比;用"一句话";诚实评估不粉饰;词汇必须与 `docs/SOP/说明/词汇表.md` 一致(Effect/Event,禁止 Command/Result)。
5. **代码引用** → 文档中的代码块必须与真实代码一致;写完后用 Grep 核对关键签名,发现过期引用立即修正。
6. **更新索引** → 新文档:加入对应目录的 CONTENT.md / 需求清单;重命名:同步所有引用它的文档。
7. **收尾** → 状态标记 + 变更记录表(日期 | 变更)追加一行;文档提交随代码提交走。

## 4. 滚动更新规则

- 每个文档底部有 `## 变更记录` 表,每次修改追加一行,不改历史。
- 状态标记只有四个:`初稿 / 梳理稿 / 修订稿 / 已落地`;结构变更后由"初稿→已落地",复查后的修订写"修订稿"。
- 代码重构后必须检查受影响文档(见 `rules.md` 的联动清单),否则文档会过期(例:07 修订删了 CommandPort,旧文档里的签名就是教训)。
- 说明/ 四件套是"快照":任何结构性变更都要问"项目树/拓扑/词汇/演进史 哪些要更新"。

## 5. 细节规则与模板

- 完整规则(命名/编号/口吻/边界):见 [rules.md](./rules.md)
- 模板:见 [templates/](./templates/)

## 6. 完成后检查清单

- [ ] 文档位置正确(四分类不混淆)
- [ ] 结构符合骨架
- [ ] 词汇与词汇表一致(无 Command/Result)
- [ ] 代码引用与真实代码一致
- [ ] 对应 CONTENT/清单已更新
- [ ] 变更记录已追加
